# I18n

Vueform translates on three layers. The framework's own strings are **tags** looked up in the active locale, the texts you write accept **locale maps** the same locale resolves at render time, and a **translatable input** translates what the _user_ writes, holding every language's copy in the model. The first two re-translate every form on the spot when the locale switches; the third stores content in the data, not the UI language.

## Locales

A locale is the dictionary everything else reads — it supplies the translations for the built-in tags, and its code is what locale maps are keyed by. Vueform ships with the following locales, exported from `@vueform/ui/locales`:

<!-- #region available-locales -->

| Code | Name |
| --- | --- |
| `de_DE` | 🇩🇪 Deutsch |
| `en_US` | 🇺🇸 English |
| `hu_HU` | 🇭🇺 Magyar |

<!-- #endregion available-locales -->

The [Full Bundle](/guide/code-splitting#the-full-bundle) (`@vueform/ui/bundle`) registers `en_US` and sets it active. The `locales` config option **replaces** that map — it never adds to it — so to offer another language next to English, list both:

```ts
import { createVueform } from '@vueform/ui/bundle'
import { en_US, de_DE } from '@vueform/ui/locales'

createVueform({
  locales: { en_US, de_DE },
  locale: 'de_DE',
})
```

`locale` names the active code, and an empty `locale` falls back to the first registered key. The [Full Bundle](/guide/code-splitting#the-full-bundle)  pre-sets it to `'en_US'`, though — replace `locales` with a map that has no `en_US` and the active code points at nothing, leaving every built-in string as its raw tag. Set `locale` whenever `en_US` isn't in your map.

The bare `@vueform/ui` entry registers no locales and no `i18n` module at all — see [Modular Setup](/guide/code-splitting#modular-setup) and [Modules](/guide/modules#leaving-a-module-out) for what running without the module means (raw tags, plus a dev warning on locale switches).

The registered set is fixed when `!createVueform()` runs, so pass every locale your app offers up front.

### Fallback Locale

A locale doesn't have to be complete. `fallbackLocale` (default `''`, meaning no fallback) is consulted for any tag the active locale lacks, which makes partial locales practical:

```ts
import { createVueform } from '@vueform/ui/bundle'
import { en_US } from '@vueform/ui/locales'

const fr_FR = {
  steps_back: 'Retour',
  steps_next: 'Suivant',
  steps_finish: 'Terminer',
  file_button_text: 'Choisir un fichier',
}

createVueform({
  locales: { en_US, fr_FR },
  locale: 'fr_FR',
  fallbackLocale: 'en_US', // [!code highlight]
})
```

A tag resolves active locale → fallback locale → the raw tag string, and an empty-string translation counts as missing and falls through too. The same fallback serves the [Locale Maps](#the-resolution-chain) on your own props.

### Changing the Active Locale

`!useI18n` returns the i18n module. Its `locale` is a writable computed ref of the active code, and `setLocale(code)` switches it (`set` is an alias):

```ts
import { useI18n } from '@vueform/ui'

const { locale, setLocale } = useI18n()

locale.value // 'en_US'
setLocale('de_DE')
```

A switch re-resolves every [tag](#locale-tags) and [locale map](#locale-maps) in every form immediately. Validation errors already on screen re-render in the new language without re-running a single rule — see [Locale Tags](/guide/validation#locale-tags).

The `locale` config option also accepts a `ref`, which keeps the source of truth outside Vueform — a Pinia store, a URL param. The binding is two-way, so writing the ref switches the locale and `setLocale()` writes back into your ref:

```ts
import { ref } from 'vue'
import { createVueform } from '@vueform/ui/bundle'
import { en_US, de_DE } from '@vueform/ui/locales'

export const appLocale = ref('en_US')

createVueform({
  locales: { en_US, de_DE },
  locale: appLocale, // [!code highlight]
})
```

Outside a setup context — a store, a route guard — the same module is available as `!vueform.useI18n()` on the [instance](/guide/vueform-instance#outside-a-setup-context), or by passing the instance to `useI18n(vueform)`. Inside [event handlers](/guide/event-handlers) and [dynamic prop](/guide/dynamic-props) functions, the received context carries it as `$i18n`. On an SSR server the active locale lives on the instance, so a module-scope instance would share it across requests — see [Cross-Request State](/guide/ssr#cross-request-state).

## Locale Tags

Every built-in string is a tag — a key resolved through the active locale at render time. The tags fall into a handful of families — `rule_*` for validation messages, `steps_*` for wizard navigation, `file_*` for the file-picker button, `sr_*` for screen-reader labels, and `expression_error` for expression engine errors.

### Writing a Locale

A locale is a flat object of tag → string. All shipped locales share the same key set, so `en_US` is the reference when writing a new language.

The same object is how you override built-in wording app-wide — spread a shipped locale and replace the keys you want. Your own tags can live right next to the built-in ones:

```ts
import { createVueform } from '@vueform/ui/bundle'
import { en_US } from '@vueform/ui/locales'

createVueform({
  locales: {
    en_US: {
      ...en_US,
      steps_next: 'Continue', // override a built-in tag
      welcome: 'Welcome, {name}!', // add your own
    },
  },
})
```

Overriding a tag changes the wording everywhere. Wording for a single form or element goes through props instead — [`nextLabel`](/guide/multi-page-forms#navigation-bar-options) for a wizard button, or `ruleMessages` for validation messages. How rule names map onto the `rule_*` tags, the typed `_string` / `_numeric` / `_array` / `_file` variants included, is [validation](/guide/validation#locale-tags)'s territory.

### Translating in Your Code

The module's `t(tag, params?)` resolves a tag through the same active → fallback → raw-tag chain. Its `tag` argument is typed as `LocaleTag`, so built-in tag names autocomplete while any string is still accepted:

```ts
import { useI18n } from '@vueform/ui'

const { t } = useI18n()

t('steps_next') // 'Next'
t('welcome', { name: 'John' }) // 'Welcome, John!'
```

`tags` is the merged record of the fallback and active locales, and reads from it are reactive. The full member list is at [`useI18n`](/api/composables/useI18n).

### Parameters

`{name}` tokens in a tag's value are filled from `t()`'s second argument, as `welcome` above shows. A token with no matching param stays in the text as-is. To substitute on a string that isn't a tag, `replaceParams(msg, params)` does the same on its own.

The token syntax itself is the `localeParamPattern` config option (default `/\{(\w+)\}/g`). Its first capture group must yield the parameter name, and it always runs globally — other flags are dropped:

```ts
createVueform({
  localeParamPattern: /:(\w+)/g, // tokens look like :name
})
```

The pattern applies to every string, the shipped locales included — their `{attribute}`, `{min}`, and friends stop resolving under a different syntax unless you rewrite those locales to match.

## Locale Maps

Tags translate Vueform's built-in strings — the texts you write yourself translate in place. Labels, placeholders, help texts, button captions, and success messages are [`TProp`](/guide/dynamic-props)s, and every `TProp` accepts a **locale map** instead of a string. A locale map is a plain object keyed by locale codes:

```ts
{
  email: {
    type: 'text',
    label: { en_US: 'Email address', de_DE: 'E-Mail-Adresse' },
    placeholder: { en_US: 'you@company.com', de_DE: 'sie@firma.de' },
  },
}
```

The active locale picks the matching entry at render time and every map re-resolves the moment the locale [switches](#changing-the-active-locale), with no message files and no keys to maintain — each translation lives next to the prop it belongs to.

The keys are the codes you [register under `locales`](#locales). They aren't type-checked against the registered set, so a mistyped code doesn't error — its entry is simply never matched and the lookup falls through [the resolution chain](#the-resolution-chain).

### Which Props Take Maps

Text a person reads is a `TProp` and takes a map; values the framework consumes — icons, numeric bounds, severities — are `DProp`s and don't. The full per-prop breakdown is at [where each type appears](/guide/dynamic-props#where-each-type-appears).

Beyond the obvious labels, placeholders, and help texts, the less expected `TProp`s are the form's `successMessage` and `redirect` (a per-locale redirect URL works), a button's `text` and even its `href` / `to`, a repeater's `addLabel` and `removeLabel`, [page](/guide/multi-page-forms) labels, and [addons](/guide/element-layout#addons):

```ts
const [MyForm] = useForm({
  schema,
  successMessage: { en_US: 'Thanks, saved!', de_DE: 'Danke, gespeichert!' },
  redirect: { en_US: '/en/thanks', de_DE: '/de/danke' },
})
```

What `successMessage` and `redirect` do once the form submits is [submit](/guide/submit#after-success)'s territory. Two more surfaces take maps in their own ways — validation messages in `ruleMessages` and in `!createRule`'s `message` (see [multilingual messages](/guide/validation#multilingual-messages)), and the language names of [multilingual inputs](#available-languages). On the PrimeVue integration, `info`, `tooltip`, `floatLabel`, and `ifta` are `TProp`s as well, so those texts translate the same way.

What doesn't take maps are option **item labels** — the `items` of select, radio, and checkbox elements aren't `TProp`s, so a map there is never resolved. [Localizing Your Own Content](#localizing-your-own-content) shows how to translate them anyway.

### The Resolution Chain

A map doesn't need an entry for every registered locale. A prop resolves to the first non-empty entry of:

1. the active locale's entry
2. the [`fallbackLocale`](#fallback-locale)'s entry
3. the map's first entry

```ts
// locale: 'fr_FR', fallbackLocale: 'en_US'
{
  name: {
    type: 'text',
    label: { fr_FR: 'Nom', en_US: 'Name' }, // → 'Nom' (active locale)
    help: { en_US: 'Legal name, please' }, // → 'Legal name, please' (fallback)
    placeholder: { de_DE: 'Name eingeben' }, // → 'Name eingeben' (first entry)
  },
}
```

An empty-string entry counts as missing and falls through to the next step, and without a configured `fallbackLocale` step 2 is skipped. When no step yields a non-empty string, the prop falls back to its own default — exactly as an empty plain string would.

### Maps and Expressions

Each entry of a map is an ordinary prop string, so it can hold [expression](/guide/expressions) blocks. Localization runs **before** expression resolution — the active locale picks the entry first, then its `{...}` blocks resolve against the live form data:

```ts
{
  name: { type: 'text', label: 'Name' },
  bio: {
    type: 'textarea',
    label: { en_US: 'Bio of {name}', de_DE: 'Biografie von {name}' },
  },
}
```

`{name}` here references the `name` element, not a [locale-tag parameter](#parameters) — `localeParamPattern` plays no part inside maps.

The inverse doesn't hold. An expression resolves to a string and never to a map, so an expression can't pick between translations — the map picks first.

### Tags Instead of Maps

A plain-string prop is never looked up as a locale tag. `label: 'steps_next'` renders the literal text `steps_next` even though that tag exists in every shipped locale — among props, only validation messages resolve tags on their own (see [locale tags](/guide/validation#locale-tags)). When translations should live in locale files instead of the schema, use the prop's function form and the context's `$i18n` module:

```ts
{
  email: {
    type: 'text',
    label: (el$) => el$.$i18n.t('email_label'),
  },
}
```

`t()` reads the active locale inside the prop's computed, so the label re-evaluates on every locale switch. Registering the `email_label` tag is covered in [writing a locale](#writing-a-locale).

Choosing between the two is mostly a storage question. Inline maps keep translations next to the schema and survive JSON serialization, while tags centralize them in locale files or a [custom i18n backend](#custom-i18n-backend).

### Localizing Your Own Content

The resolution behind text props is yours to call. `!useI18n` exposes `localize(map)`, which returns the entry picked by [the chain above](#the-resolution-chain), and `localizeObject(record)`, which runs `localize` on every value of a `{ key: map }` record.

That closes the item-label gap — `items` accepts a ref, and `localizeObject` returns exactly the `Record<string, string>` shape items take:

```vue
<script setup lang="ts">
import { computed } from 'vue'
import { useForm, useI18n } from '@vueform/ui'

const { localizeObject } = useI18n()

const countries = computed(() =>
  localizeObject({
    de: { en_US: 'Germany', fr_FR: 'Allemagne' },
    fr: { en_US: 'France', fr_FR: 'France' },
  })
)

const [MyForm] = useForm({
  schema: {
    country: { type: 'select', label: 'Country', items: countries },
  },
})
</script>

<template>
  <MyForm />
</template>
```

The `computed` re-runs on locale switches, so the option labels follow the active locale like any translated prop. The same calls work in your own components rendered inside a form — [`useContext`](/guide/context#useContext) hands you the nearest component's context, which carries the module as `$i18n`.

## Custom I18n Backend

To route Vueform's strings through an i18n system your app already runs, replace the built-in translator wholesale with `$i18n.adapter`. An adapter is an `I18nAdapter` — a function receiving the merged i18n options (`locales`, `locale` as a ref, `fallbackLocale`, `localeParamPattern`, plus any other `$i18n` overrides) and returning the full `I18nModule` surface: `locale`, `tags`, `locales`, `fallbackLocale`, `t`, `setLocale`, `set`, `replaceParams`, `localize`, and `localizeObject`.

```ts
import { computed, ref, unref } from 'vue'
import { createVueform } from '@vueform/ui/bundle'
import type { I18nAdapter } from '@vueform/ui'

const myAdapter: I18nAdapter = (options) => {
  const current = ref(unref(options.locale) || '')
  const setLocale = (code: string) => { current.value = code }

  return {
    locale: computed({ get: () => current.value, set: setLocale }),
    tags: {}, // the merged fallback + active tag record
    locales: options.locales ?? {},
    fallbackLocale: options.fallbackLocale ?? '',
    t: (tag, params) => tag, // translate a tag, filling {param} tokens
    replaceParams: (msg, params) => msg, // substitute tokens in a plain string
    setLocale,
    set: setLocale,
    localize: (msg) => '', // resolve a locale map to a string
    localizeObject: (obj) => ({}), // resolve every value of a { key: localeMap } record
  }
}

createVueform({
  $i18n: { adapter: myAdapter }, // [!code highlight]
})
```

Once installed, everything that reads strings goes through it — components, validation messages, the expression engine's error text, `useI18n()`, and `vueform.useI18n()` alike. The rest of the `$i18n` keys mirror the top-level options for module-scoped overrides — see [configuration](/guide/configuration#internationalization).

## Multilingual Inputs

Tags and maps translate the UI — a **translatable input** translates the data. One field's model value holds every language's copy side by side, the shape content-management forms need. Its languages are content slots in the data, not the UI language, so they're configured separately from locales.

### Translatable Elements

Set `translate: true` on an element and give it a `languages` map, and its model value becomes an object keyed by language code instead of a single string:

```ts
{
  bio: {
    type: 'text',
    label: 'Bio',
    translate: true,
    languages: { en_US: 'English', fr_FR: 'French' },
  },
}

// model: { bio: { en_US: 'Hello there', fr_FR: 'Bonjour' } }
```

`translate` on its own is inert — the element only becomes translatable once at least one language resolves from the element, the form, or the global config, and the config ships none by default. [Available Languages](#available-languages) covers where the map can live.

The input shows one language at a time, and typing writes the active language's entry. The element's [context](/components/VfText#context) mirrors the split — `value` is the active language's entry, `model` the full language-keyed object.

Among the built-in elements, `!VfText` and `!VfTextarea` are translatable. Custom elements built on `!VfField` get the same capability and behave exactly as this section describes — see [Wrapping a Widget with `VfField`](/guide/components#wrapping-a-widget-with-VfField) for how to build one.

#### Values and Defaults

`default` takes a language-keyed object, and languages missing from it start at the element's empty value. A plain-string `default` is applied to every language at once.

Values written from outside follow the same shape. Hand the [Model API](/guide/model#the-model-api) a language-keyed object and it replaces every language at once — `form$.set('bio', { en_US: 'Hi', fr_FR: 'Salut' })` — or reach a single language by its path, `form$.set('bio.fr_FR', 'Salut')`. An element `v-model` or seeded value for a translatable element must be an object; a scalar throws `Multilingual model must be an object`.

With `!defineSchema`, `translate: true` plus a literal `languages` map types the element's model as an object keyed by exactly those codes; without a `languages` prop the keys stay `string` — see [model](/guide/model#external-model) for how schema typing flows into the model.

### Available Languages

A language map pairs codes with display labels — the codes become the model's keys, the labels are what the switchers show. The map can live at three levels, and the most specific one wins:

| Level | Where |
| --- | --- |
| Global | `languages` in `createVueform()` |
| Form | `languages` on `!VfForm` or `!useForm` |
| Element | the element's `languages` prop |

The element form appeared above and the form level comes with the [form-level switcher](#form-level-language-switcher); the global map covers every form in the app:

```ts
createVueform({
  languages: { en_US: 'English', fr_FR: 'French' },
})
```

The config option's type and default live in [configuration](/guide/configuration#languages).

Labels can themselves be [Locale Maps](#locale-maps), resolving with the active locale through the same chain as any translated prop:

```ts
createVueform({
  languages: {
    en_US: { en_US: 'English', fr_FR: 'Anglais' },
    fr_FR: { en_US: 'French', fr_FR: 'Français' },
  },
})
```

#### Headless Models

A `!useModel` instance expands translatable values with its own `languages` option, falling back to the global config — element `languages` props still win. Pass it the same map the attaching form gets, so both agree on the model's shape:

```ts
const model = useModel({ schema, languages: { en_US: 'English', fr_FR: 'French' } })
```

`!useForm`'s internal model takes the form's `languages` automatically. Headless reads of a translatable value — the `value` that [expressions](/guide/expressions) and rule references consume on an unmounted element — resolve to the first language, since only a mounted form switches languages.

### Per-Element Language Switcher

Every translatable element ships its own switcher — a compact language select rendered beside the input, after any addons the element defines (the placement belongs to [element layout](/guide/element-layout#the-language-addon)).

It starts on the element's own `language` prop when set; otherwise on the first key of the element's own `languages`; otherwise on the form's active language. Each element's choice is its own, so one element can edit a different language than its neighbors — French `body` beside English `title`, the side-by-side translation workflow. Screen-reader users hear which language an input is editing — see [ARIA Attributes](/guide/accessibility#aria-attributes).

The element's `#language` [slot](/guide/slots) replaces the select entirely, receiving the active `language` and the `languages` map, while the `language` [part](/guide/parts) merges props onto the `!VfAddon` that renders it.

### Form-Level Language Switcher

Editing many translatable elements one inline switcher at a time doesn't scale. Setting `multilingual` on the form renders a `!VfLanguages` button bar at the top of the form — before any tabs or steps — that drives every translatable element at once:

```ts
const [MyForm, form$, formReady] = useForm({
  multilingual: true,
  languages: { en_US: 'English', fr_FR: 'French' },
  schema: {
    title: { type: 'text', label: 'Title', translate: true },
    body: { type: 'textarea', label: 'Body', translate: true },
  },
})
```

Picking a language realigns every translatable element to it, discarding any per-element choice. An element whose own `languages` lack the picked code stays where it is, and Vueform logs a warning.

The same control is available in code on the [form context](/guide/context#form-context). The `language` prop sets the starting language (the first key of `languages` by default), `form$.language` reads the active one, `form$.languages` is the resolved label map, and `form$.selectLanguage(code)` switches:

```ts
formReady((form$) => {
  form$.language // 'en_US'
  form$.selectLanguage('fr_FR')
})
```

These drive the elements whether or not `multilingual` is set — the prop only adds the switcher UI.

Languages holding validation errors are marked on the switcher — each option carries `aria-invalid` and `data-invalid` — so the user sees which translation needs attention without visiting each one. The set behind the markers is `form$.invalidLanguages`.

The form's `#languages` slot replaces the whole switcher (scope `languages`, `language`, `invalidLanguages`, `select`, `bindings`), and `#language` replaces each option — see the [`!VfForm` slots reference](/components/VfForm#slots).

### Validating Languages

A translatable element's rules run once per language. Each language validates independently and holds its own result, and the element is invalid while any language is. Error messages carry the language's label, so the user knows which translation failed:

```
The Bio must be at least 10 characters. (English)
The Bio field is required. (French)
```

The per-language results live on the element's [context](/components/VfText#context) — `invalidLanguages`, `validation` keyed by language, `currentValidation` for the active one, and `validateCurrent()` to validate just that.

To validate languages differently, key the `rules` prop by language code — the spec and how entries combine live in [Multilingual Rules](/guide/validation#multilingual-rules). Language-keyed rules on a non-translatable element throw.
