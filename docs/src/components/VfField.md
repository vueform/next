# VfField

<!-- @tabs -->

<!-- @tab Usage -->

## Basic Usage

`VfField` is a headless element for wiring any custom input into a Vueform form. It renders no input of its own — instead it participates in the form's data model, validation, conditions, and layout like any other element, and exposes its full [Context](#context) through the default slot, so you can bind your own markup via `context.value` and `context.handleInput`.

::: usage center model

```vue [Preview]
<VfField name="color" default="#3b82f6">
  <template #default="{ context }">
    <input type="color" :value="context.value" @input="context.handleInput" />
  </template>
</VfField>
```

```vue [Schema]
<script setup lang="ts">
import { defineSchema, defineSlot, useForm } from '@vueform/ui'
import { h } from 'vue'

const schema = defineSchema({
  color: {
    type: 'field',
    default: '#3b82f6',
    slots: {
      default: defineSlot('VfField.default', {
        props: ['context'],
        setup({ context }) {
          return () =>
            h('input', {
              type: 'color',
              value: context.value,
              onInput: context.handleInput,
            })
        },
      }),
    },
  },
})

const [Form] = useForm({ schema })
</script>

<template>
  <Form />
</template>
```

:::

## Options

The `options` prop passes arbitrary data into the slot context via `context.options`, which is useful for parameterizing the custom input — especially in schema-driven usage.

::: info
The [`alpha`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/alpha#browser_compatibility) and [`colorspace`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/colorSpace#browser_compatibility) attributes used below have limited browser support.
:::

::: usage center model

```vue [Preview]
<VfField
  name="color"
  default="oklab(50% 0.1 0.1 / 0.5)"
  :options="{ alpha: true, colorspace: 'display-p3' }"
>
  <template #default="{ context }">
    <input
      type="color"
      :value="context.value"
      :alpha="context.options?.alpha || undefined"
      :colorspace="context.options?.colorspace"
      @input="context.handleInput"
    />
  </template>
</VfField>
```

```vue [Schema]
<script setup lang="ts">
import { defineSchema, defineSlot, useForm } from '@vueform/ui'
import { h } from 'vue'

const schema = defineSchema({
  color: {
    type: 'field',
    default: 'oklab(50% 0.1 0.1 / 0.5)',
    options: { alpha: true, colorspace: 'display-p3' },
    slots: {
      default: defineSlot('VfField.default', {
        props: ['context'],
        setup({ context }) {
          return () =>
            h('input', {
              type: 'color',
              value: context.value,
              alpha: context.options.alpha || undefined,
              colorspace: context.options.colorspace,
              onInput: context.handleInput,
            })
        },
      }),
    },
  },
})

const [Form] = useForm({ schema })
</script>

<template>
  <Form />
</template>
```

Bind it to the one event that means "the user changed it": `@input` for native text inputs, `@change` for native checkbox / radio / select / file controls, `@update:model-value` for components — alongside `v-model`, or without it.<br><br>Accepts the new value or the native event carrying it (an event's value is read the way `v-model` reads it); a plain value may pass the originating event as the second argument so composition filtering still applies. Events fired during an IME composition session are ignored — the composed text arrives once, when the session ends.<br><br>The value is written to the model only when the model doesn't hold it yet — with `v-model` in place this is a pure user-input notification, without it `handleInput` performs the write itself. Values resolved from native events are only adopted while `canonicalDomValue` is on; on formatted inputs (masks) the event carries display text, so only the notification fires, with the current model value as the payload. Either way it reports the input: fires the `input` event with `(value, event, context$)` and triggers `validateOn` / expression untracking. It does **not** touch the interaction states — `visited` and `touched` come from `handleFocus` / `handleBlur`. |
| [`handleKeydown()`](!code#context.handleKeydown "(e: Event) => any") | Fires the keydown event on the element. |
| [`handleKeyup()`](!code#context.handleKeyup "(e: Event) => any") | Fires the keyup event on the element. |

| [`handleBlur()`](!code#context.handleBlur "(e: Event) => void") | Fires the blur event on the element. |
